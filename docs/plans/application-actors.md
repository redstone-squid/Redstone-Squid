# Acting context across Squid

Every public application operation should receive a required, keyword-only acting context, including reads and scheduled jobs. The HTTP, Discord, CLI and worker entry points establish it once per invocation. A service calling another service forwards the context. Pure calculations, repository lookups and external clients only need the facts their contracts use.

## Identity and authority

Extend the existing Actor and ActingContext in squid/core/actors.py. Use explicit variants for an unidentified visitor, a guest session, an identified user (account or Discord identity), an external service credential and a registered worker. Preserve the existing operator and effective actor distinction for impersonation. Keep credential restrictions and guild authority attached to the invocation. A worker name identifies the consumer or scheduled task. A run or attempt ID identifies one execution.

For queued work, model the original invocation and the current executor separately. For example, when an operator impersonates a user to request a rebuild, the rebuild transaction must be attributable to the worker, linked to the request, and traceable to both people. Store stable identity references and correlation IDs. Resolve current authorization where execution requires it. Never serialize bearer tokens, Discord role lists or permission snapshots as authority for a future job.

Targets, owners, voters being recounted and recipients remain explicit domain arguments. Derive the caller from the context. A public read may accept an anonymous visitor without allocating a session or writing an audit row.

## Delivery and agent ownership

Use one integration lead and up to three parallel implementation subagents. The lead owns shared contracts, service bundles, migration ordering and cross-slice integration. Give each agent a disjoint domain slice including its ports, callers, fakes and tests. Assign shared router, worker registry and schema files to one owner per wave. Land small vertical commits with passing callers. Temporary migration shims must have named callers and be removed before completion.

1. **Inventory and contracts.** Three agents map (a) core public methods and their direct callers, (b) HTTP, Discord, CLI, browser and operational entry points, and (c) background callbacks, queues, outbox and transaction commits. Start at ApiServices, BotServices and WorkerServices in squid/runtime.py and SubmissionServices in squid/core/submissions/bootstrap.py. Follow direct imports, command/query handlers, application.py modules, scripts and worker-only paths. Keep a checked migration table by method with caller, identity source, target/owner, authorization, transaction or handoff, tests and assigned slice. Classify internal helpers with a reason. The lead lands the context types, constructors, stable references and test factories before fan-out. Preserve existing user replay keys and impersonation audit links. Give guests separate replay namespaces and reject identity-dependent replay for unidentified visitors.
2. **Establish trusted boundaries.** One agent adapts HTTP authentication and browser sessions, another migrates Discord resolution and interaction callbacks, and a third introduces worker contexts and durable provenance. Preserve HTTP account grants intersected with credential scopes, ownerless service keys, consent rules, operator rate limits, header precedence and existing authentication errors. Discord must resolve guild facts at the action, including modal submissions, rerenders and listeners. Keep bot maintenance distinct from commands a human initiated. CLI requests retain the server-authenticated credential identity. Exercise /v1/session, the web client, CLI and Minecraft contracts. Classify credential lookup as a bootstrap dependency so resolving identity does not require an already-resolved actor. Local administrative scripts use a named execution identity with a defined permission policy.
3. **Prove end-to-end behavior.** Land three reference paths before mechanical migration. Use record version pinning and rebuilding to move the permission check into a single administrative operation before either write. Use a public catalogue read to prove anonymous access stays cheap. Use submission finalization to prove a durable handoff survives restart and retries. Replace reconstruction of the caller from a draft owner with explicit origin, executor and ownership checks. Preserve reauthorization at execution. Add a supported query or operator inspection path from a committed change to its executor and originating invocation.
4. **Migrate remaining domains by vertical slice.** Agent A owns accounts, auth, CLI auth, Minecraft auth, permissions, edit execution, replay/idempotency and notifications. Agent B owns submissions, artifacts, schematics, media, builds, catalogue, records, versions, tags, search and suggestions. Split intake/finalization and catalogue/read models into successive batches. Agent C owns voting, posts, messages, starboard, settings, community, reactions, sync, events and diagnostics. Assign remaining inventory rows explicitly, including sponsors, external integrations, locks and cleanup operations wherever they expose a use case. The lead reconciles cross-domain calls after each batch. Check privileges inside the application operation where applicable, while retaining adapter checks that shape the UI or enforce transport-specific access.
5. **Reserve guest identity.** Model a stable guest principal for future callers. Guest session issuance, resource ownership and sign-in claims are outside this implementation.
6. **Remove transition paths and enforce coverage.** Delete implicit anonymous defaults, ad hoc Actor reconstruction and adapter-only authorization for migrated use cases. Add an architecture test over the classified application surfaces requiring the context parameter on each public entry point, plus focused behavior tests for nested forwarding, credentials, ownership and durable handoffs. Reconcile every inventory row and document how to add a new entry point or worker.

## Persistence and rollout

Add schema support before changing producers. Record provenance alongside the enqueue or event write in the same transaction. Restore it at claim and dispatch. Preserve the origin across chaining and retries, and record the current consumer and attempt separately. A periodic maintenance job originates as its registered worker. A multi-item batch can have several origins, so associate provenance with each durable item. For coalesced jobs, retain contributing causes or record an explicit aggregation rule. Never infer a historical operator from a resource owner.

Cover PostgreSQL enqueue triggers as well as Python producers. Set transaction-local provenance before trigger-producing writes and verify pooled connections cannot inherit a previous invocation. Keep the durable attempt identity independent of queue claim tokens and retain attribution after queue deletion. Trace worker/events.py and supervised callbacks in the bot and API as well as WorkerJobSpec loops.

Roll out readers that accept legacy rows, then writers that populate provenance, then consumers that require it for new records. Test mixed-version delivery, old queue rows, retries, dead letters, rollback and restart. Keep historical unknowns distinguishable from anonymous requests. Apply retention and access controls to provenance and guest identifiers. Make existing impersonation auditing and SQL unit-of-work hooks cooperate with the new attribution. Keep Discord reactive transaction history scoped to its existing purpose.

## Acceptance

- An operator can trace a worker mutation after restart to its named executor, attempt and originating request, including impersonation when applicable. Retrying preserves origin and existing idempotency behavior.
- An unauthorized caller invoking a privileged service directly fails before mutation. Account-owned credentials stay scope-limited. Targets and owners never implicitly grant the caller authority.
- Public browsing requires no cookie. A guest principal is distinct from an unidentified visitor and receives no new permissions.
- Every inventoried entry point has a classification, migrated callers and an executable check appropriate to its behavior. Run focused tests after final edits, changed-file lint and whole-project Pyrefly. Run the full suite for the integrated refactor and validate schema upgrades against populated data before enabling features.
